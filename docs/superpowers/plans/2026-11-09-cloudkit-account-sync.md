# CloudKit Account Sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Automatically synchronize accounts, secrets and transferable saved sessions across the user's Macs in a Developer ID–signed, notarized DMG.

**Architecture:** Keep the local catalog authoritative for offline use and use a private CloudKit zone with CKSyncEngine for transport. Merge versioned fields and durable tombstones through a crash-safe journal, encrypt payloads with AES-GCM and iCloud Keychain keys, and stage incoming sessions until explicit adoption through existing services.

**Tech Stack:** Swift 6, macOS 14+, Swift Testing, CloudKit/CKSyncEngine, CryptoKit, Security, SwiftUI, WebKit, existing Chrome CDP and native credential adapters, XcodeGen and Make.

**Spec:** `docs/superpowers/specs/2026-11-09-cloudkit-account-sync-design.md` (user-approved on 2026-11-09).

## Global Constraints

- Minimum macOS version: 14.0. Swift version: 6. Strict concurrency and warnings-as-errors remain enabled.
- Bundle ID: `com.linda.CodexPlusBar`. Developer team: `2Z8N5KTWQZ`, as observed in the installed app's signature.
- Proposed CloudKit container: `iCloud.com.linda.CodexPlusBar`. Confirm/register it in the developer account during provisioning.
- Use CloudKit's private database, a custom zone named `AccountSyncV1`, and `CKSyncEngine`.
- A release uses the Production CloudKit environment and the corresponding push environment; provisioned development builds use Development. These environments are deliberately separate.
- Package with Developer ID Application signing, hardened runtime, notarization and stapling. App Store Connect is not part of this workflow.
- Sync is opt-in on each Mac; saved-session inclusion initially defaults to on. Turning either off preserves existing copies, cancels relevant work and prevents new publication/adoption until enabled again.
- Encrypt payloads with random 256-bit AES-GCM keys. Limit each encoded plaintext and each staged encrypted asset to 16 MiB; account for envelope/tag overhead before accepting plaintext near the limit.
- Private files use mode 0600 and directories mode 0700. Real credentials, cookies, key material and decrypted payloads must not enter logs or fixtures; tests generate synthetic values in memory.
- Preserve per-Mac browser IDs, native credential IDs, active selections, receipts, and unknown/inactive providers. Match cloud profiles by UUID only.
- A tombstone dominates every update to that UUID. Explicit restore/import can create a new UUID; routine delivery never resurrects a deleted profile.
- Remote sessions are an inbox, not active credentials. External apps may independently rotate refresh tokens; retain Repair and truthful network-versus-rejection reporting.
- Read `Learnings.md` before implementation. Keep unrelated changes, the installed application, normal browser profiles and real credential stores out of synthetic verification.

## Review Focus

- A newer client sends an unknown schema/field: an older client must retain/quarantine it without overwriting its remote record (Tasks 1, 4).
- An unreadable or missing local catalog appears empty: it must never cause mass cloud deletions (Tasks 2, 5).
- Disk space runs out after fetching an asset: restart must replay the record, not skip it through a persisted cursor (Tasks 2, 4).
- A restore commits immediately before a crash: startup must remain paused, with no deletion publication from restored absence (Task 5).
- A remote update arrives while a local detail draft is open: saving the draft must preserve remote fields the user never edited (Task 5).
